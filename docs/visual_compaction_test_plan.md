# 「失忆鹈鹕」测试计划：压缩之后，鹈鹕还画得对吗？（2026-10-19）

## 要回答的问题

InfiniteUsage 最省钱的一招是提前压缩（Claude Code 约 300K 就压缩，默认约 967K）。风险是：压缩后 agent 忘掉早先定下的细节。
这个测试把「忘没忘」画出来：早早定好一张图的细节，中间塞大量无关工作把上下文撑大，压缩，最后让它画。忘了什么，图上一眼就能看出来。

和 Simon Willison 的「鹈鹕骑自行车」挂钩：最后一句提示词就是那句经典的 *Generate an SVG of a pelican riding a bicycle*，观众认得；区别是这次图里的细节是很久以前、压缩之前定的。

## 设计

|---|---|---|
| 1 | 画布 `viewBox="0 0 800 600"` | 正则 |
| 2 | 鹈鹕的围巾 `#E4572E` | 颜色出现 |
| 3 | 自行车车架 `#8338EC` | 颜色出现 |
| 4 | 太阳 `#FFB703`，在左上角 | 圆心 x < 267、y < 200 |
| 5 | 天空渐变 `#FFD166` → `#06D6A0` | 两个颜色都在渐变里 |
| 6 | 路边牌子写着 `IU-42`（后面会改） | 见第 11 条 |
| 7 | 车筐里一条鱼 `#3A86FF` | 颜色出现 |
| 8 | 天上 5 只鸟，描边 `#2B2D42` | 这个颜色的线条正好 5 个（每只画成左右两笔、共 10 个也算） |
| 9 | 每个车轮 6 根辐条，描边 `#5C677D` | 这个颜色的线正好 12 根 |

### 2. 中间的无关工作（把上下文撑大）

第 3~N 轮做和画图无关的真实活：读本仓库的大文件，回答里面的问题。比如「读 bench/simulate.py，列出所有函数名」，或者读一份 20K token 的日志找错误。
内容固定、可重复，每组读的一样多。

### 3. 最后一轮

## 怎么把开销压到最小

1. **缩小比例，机制不变**：压缩是不是丢细节，和窗口多大关系不大。用 `CLAUDE_CODE_AUTO_COMPACT_WINDOW=100000`（实测约 67% 时触发，也就是 6.7 万左右），中间工作撑到 9 万上下文就够了。比真的撑到 30 万便宜大约 5 倍
2. **中间工作一次读得多**：少几轮，每轮读一大块，大部分按缓存读计价（0.1 倍）
3. **先用免费模型把流程跑通**：OpenCode + 免费模型当宿主（它也会自动压缩），把脚本、检查器、渲染全部调通，付费额度为零。免费模型画得丑没关系，这一步只为排错
4. **付费只跑 Sonnet**，样本小，分阶段，每一阶段看结果再决定要不要下一阶段
5. **检查器不调用模型**：12 条全部用正则和计数判断。渲染成 PNG 用本机工具（`rsvg-convert` 或浏览器截图）

## 以后可以扩成通用实验

同一套规格和检查器，宿主换成 Codex（`codex exec resume`）、OpenCode、Qwen Code 等各家，各自开或不开提前压缩，就是一张「各家 agent 压缩后还记不记得」的对比表。

## 已知局限

- 只测「记不记得早先定的细节」，不测写代码的推理能力。写代码那一面要靠修 bug 冲刺的单元测试（已有）
- 缩小比例后，摘要要概括的内容比真实 30 万上下文少，丢细节的概率可能偏低。阶段 3 的大片顺便当作一次真实比例的抽查
- 画得好不好看不打分（主观），只打 12 条客观细节

## 阶段 0 结果（2026-10-19，OpenCode + deepseek-v4.1-flash-free，付费额度 0）

| 组 | 得分 | 最大上下文 | 最后一轮上下文 | 耗时 |
|---|---|---|---|---|
| 马上画（天花板） | 12/12 | 1.7 万 | 1.7 万 | 57 秒 |
| 长上下文·不压缩 | 12/12 | 11.9 万 | 11.9 万 | 286 秒 |
| 长上下文·压缩 | 12/12 | 10.1 万 | **3.8 万**（压缩生效） | 232 秒 |
| 压缩 + 笔记 | 12/12 | 11.0 万 | 4.7 万 | 411 秒 |

- 流程全通：多轮续聊、压缩（OpenCode 服务的 summarize 接口）、打分、Chrome 渲染、四宫格。图在 `bench/results/pelican/grid_opencode_1.png`
- 检查器修了两次误判：模型会把规格里的颜色顺手用在别处（地面线、鹈鹕描边），现在按位置数：天上 y<200 且不闭合的才算鸟，从车轮中心出发的才算辐条
- **这一版太容易**：规格是一整段，压缩一次，摘要原样保住了全部 12 条，连免费模型都满分。要拉开差距，阶段 1 之前先加难度（见下）

### 加难度的办法（都还是零付费，先用免费模型试）

1. 规格分散：12 条拆到前几轮里，每轮夹一点无关工作，不再是一整段
2. 多改几次：同一个细节改两三次（IU-42 → 43 → 44 → 改回 43），测摘要能不能保住最终值
3. 压缩两次：中间工作加倍，让它压缩两轮，摘要的摘要更容易丢东西
4. 细节更琐碎：比如「左边第二只鸟比别的小」，这种不起眼的细节最容易被摘要省掉

## 加难版结果（2026-10-20，同一个免费模型，16 条）

| 组 | 得分 | 最大上下文 | 最后一轮 | 说明 |
|---|---|---|---|---|
| 马上画（天花板） | 16/16 | 2.2 万 | 2.2 万 | |
| 长上下文·不压缩 | 16/16 | 12.5 万 | 12.5 万 | |
| 长上下文·压缩两次 | **16/16** | 8.2 万 | 4.7 万 | 两次压缩都生效（8.2 万 → 3.1 万），改了 4 次的路牌、改过的颜色和数量、琐碎细节全对 |
| 压缩 + 笔记 | 无效 | 7.1 万 | — | 第一次压缩时免费模型超时，会话卡住，之后每轮都没回应。是线路问题，不算质量数据 |

**结论：用户亲口说过的规格，压缩两次也没丢。** 原因很可能是：压缩摘要优先保留用户的要求，扔掉的是大段工具输出（读进来的代码）。
所以这个测试的方向要换：真实编程里容易丢的，是**从工具输出里得到的信息**（文件里的配置值、某个函数在第几行），不是用户说的话。

### 下一版（仍然零付费）

- 把细节藏进中间读的文件里：比如某个文件里写着「路牌颜色见 `ref/config.json` 的 sign_color」，规格只说「路牌用配置文件里的颜色」。压缩后它要么记得、要么得重新去读
- 记录压缩后有没有重新去读那个文件：重读能画对是正常行为（多花一点），不读、瞎猜才算丢信息
- 压缩超时要加重试，并且超时后放弃这一组，不让会话卡几个小时（这次 C 组白等了 2.6 小时）

## 阶段 1 结果（2026-10-24，Claude Sonnet，加难版，每组 1 次，压缩窗口 10 万，约每 6.7 万压缩一次）

| 组 | 压缩次数 | 最大上下文 | 得分 | 等效 token |
|---|---|---|---|---|
| 马上画 | 0 | 4.6 万 | 16/16 | 12.9 万 |
| 不压缩 | 0 | 19.2 万 | 16/16 | 85.6 万 |
| 压缩 | 7 | 6.7 万 | **0/16**：没画，回答「这个会话里没有找到我们之前约定的鹈鹕规格……能否把那份规格贴一下？」 | 87.0 万（**+2%**） |
| 压缩 + 记笔记 | 8 | 6.9 万 | 12/16：NOTES.md 漏记了第 4 段的 4 条小细节，其余全对 | 109.1 万（+27%） |

**结论：**
1. **压缩太频繁，Claude 会彻底失忆**：7 次摘要之后，用户亲口定下的规格一条不剩。之前免费模型的满分是测试漏洞造成的（见上面的更正）
2. **太频繁的压缩也不省钱**：每次压缩本身要把整段上下文读一遍、写一份摘要，压缩后缓存还要重建。上下文只有几万 token 时，重读本来就便宜（缓存读 0.1 倍），压缩的开销反而更大
3. **记笔记能救回大部分**：写在文件里的东西不会被压缩掉。但它只记了它觉得是「规格」的部分，「小细节」那一段没记进去
4. **InfiniteUsage 的实际设置没在这里测**：我们在约 30 万压缩，真实会话平均上下文约 43.5 万，一次长会话一般压缩 1~2 次，不是 7 次。真实比例的测试（阶段 3）还要做

**对产品的启发：**
- 压缩点不能再往下压，30 万左右是「省钱」和「失忆」之间的折中，要用真实比例的测试确认
- skill 里「记笔记」那条要更硬：用户定下的每一条要求都逐条写进笔记文件，改了就更新
- 可以加一个压缩后的 hook（Claude Code 的 SessionStart，matcher 为 compact），压缩一结束就把项目笔记文件重新塞回上下文，不靠模型自己想起来

花费：Sonnet 共约 325 万等效 token（含一次因为压缩没触发而中途停掉的运行），按 API 价格约 9~10 美元

## 2026-10-24 补救：压缩后自动塞回笔记（`iu hook-compact`），C 组重跑一次（rep 3）

改了什么：
- `iu install` 新装一个 Claude Code 的 SessionStart hook（matcher 为 `compact`）：压缩一结束，把项目根目录 `NOTES.md` 的原文作为 additionalContext 塞回上下文（`iu/hook.py` 的 `compact_context`）
- skill 第 3 节改硬：用户定的每一条要求都逐条记进 `NOTES.md`（含看起来很小的细节和具体的值），改了当场更新，压缩后先读 `NOTES.md` 再继续；各家全局说明文件里的常驻规则也加了这一句
- 测试脚本的 C 组措辞同步成新版第 3 节（「逐条、含小细节、压缩后先读」），hook 只在这次运行里用 `--settings` 加，没改用户的 settings.json

| C 组 | 压缩次数 | 最大上下文 | 得分（打分脚本） | 漏掉的 | 等效 token | 用时 |
|---|---|---|---|---|---|---|
| rep 2（旧措辞，无 hook） | 8 | 6.9 万 | 12/16（runs.jsonl 里的 11/16 是当时旧版打分脚本，现行脚本重打 12/16） | 第 4 段 4 条小细节 | 109.1 万 | 796 秒 |
| rep 3（新措辞 + hook） | 9 | 6.9 万 | **10/16** | 第 4 段 4 条小细节 + 第 6 段的 IU-46、鱼 #00B4D8 | 119.3 万 | 1131 秒 |

**没达到 16/16。** hook 本身是好的：9 次压缩后每次都触发、都把 `NOTES.md` 塞回去了（会话记录里有 9 条 `hook_additional_context`），最后一轮画的内容和笔记完全一致。问题出在笔记本身没记全，原因找到了：
1. **压缩正好卡在「用户刚给新要求、还没写进笔记」的那一轮。** 第 4 段那轮：模型先 Read 了 NOTES.md，还没来得及 Edit 就触发了压缩；第 6 段那轮：一开口就压缩了。两次的压缩摘要里都完全没有那几条要求（搜不到 ladybug、IU-46 等）。rep 2 漏掉第 4 段也是同一个原因
2. **Sonnet 把这种轮次当成了可疑注入。** 压缩后它说那条要求「伪装成压缩格式、又要求不用工具又要编辑文件」，拒绝补写；后来连 hook 塞回的笔记也被它怀疑了一次（但最后画图时还是照着笔记画的）
3. 笔记写得勤也没用：只要压缩发生在「收到要求」和「写进笔记」之间，那条要求就只活在被丢掉的那段上下文里

**跟进的修复（已做，还没付费验证）：** hook 压缩后除了塞回 `NOTES.md`，再从会话记录（hook 输入里的 `transcript_path`）里取出 `NOTES.md` 最后一次保存之后用户亲手发的消息原文（不含工具结果、压缩摘要、斜杠命令；最多 6 条、3000 字，新的优先），一起塞回去，并要求先把其中的要求补进 `NOTES.md`。措辞改成中性说明（写明来源文件路径，方便模型核实），减少被当成注入的可能。
零花费回放：把 rep 3 的会话记录截到那两次压缩的位置喂给新版 hook，两次都原样带回了丢掉的那几条（第 4 段的眼睛、瓢虫、云、注释；第 6 段的 IU-46、鱼的新颜色）。付费验证见下面的 rep 4。

花费：rep 3 约 119 万等效 token（约 3~3.5 美元）；另有一次 Haiku 冒烟测试（几美分），确认 `-p` 模式下 `/compact` 之后 hook 会触发、内容能被模型看到。

**结论：** 「把规格记进 NOTES.md」+「压缩后自动塞回笔记和笔记之后的用户原话」，在每 6.7 万就压缩一次的极端设置下，把 Sonnet 从 0/16（不记笔记）、12/16（只记笔记）救到了 16/16，且没有多花钱。关键不是笔记写得勤，而是补上了「要求刚给出、还没写进笔记就被压缩」这个空档。
