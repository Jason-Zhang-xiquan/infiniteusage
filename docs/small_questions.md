# 长会话里的小问题值不值得挪走（`iu ask`）：零成本上限测试（2026-10-24）

结论：**不做 `iu ask`，只在规则里加一句提醒。** 事先定的门槛是可省上限 ≥ 5%。宽松口径的原始数字是 6.4%，刚过线，但其中一半是缓存过期后的重建费：问题挪走了，这笔钱也省不掉，只会挪到长会话的下一个回合。扣掉之后宽松上限是 3.3%。真正能离开上下文回答的岔题（严格档）只有 0.9%，扣重建后 0.65%，没到门槛。全程没调用任何模型，没花额度。

## 怎么测的

脚本：`bench/small_questions.py`（只读 `~/.claude/projects/*/*.jsonl`，不调用模型）。原始输出：`bench/results/small_questions_2026-10-24.txt`，阈值敏感性：`bench/results/small_questions_sensitivity_2026-10-24.txt`。

- 范围：Windows 本机全部 Claude Code 日志，201 个有真实用户消息的会话文件，2235 个真实用户回合，约 23.4 亿等效 token。跳过 `subagents/` 和 `isSidechain`
- 等效 token：输入 1、缓存写 2（1h）/1.25（5m）、缓存读 0.1、输出 5。每次请求取 assistant 消息的 `message.usage`，同一个 message id 全局只算一次
- 真实用户消息：`type=user`，不是 tool_result，不是 `isMeta` / `isCompactSummary`，`origin.kind` 是 human 或者没有这个字段。去掉 `<system-reminder>` 块后，开头不是 AUTO 前缀：后台任务、task-notification、粘贴、斜杠命令、「[Request interrupted」、跨会话消息等。同一句话按 (text, ts) 去重，因为续聊会复制历史
- 回合：一条真实用户消息开始，到下一条真实用户消息之前的全部请求。中间的通知、子 agent 回报都算在这个回合里
- **小问题（宽松档）**，四个阈值都可以调：
  - 用户消息 ≤ 120 字（`--max-chars`）
  - 回合内请求 ≤ 5 次（`--max-reqs`）
  - 回合内没有改文件：Edit/Write/MultiEdit/NotebookEdit，或会写文件的 Bash/PowerShell（复用 `session_explore.py` 的判断）
  - 回合第一次请求的上下文 ≥ 5 万（`--min-ctx`，上下文 = 输入 + 缓存写 + 缓存读）
- **岔题（严格档）**：宽松档里再满足下面一条
  - a) 工具只用了 WebSearch/WebFetch（记账工具不算）
  - b) 回合碰过文件，而且碰过的文件和本会话之前所有回合碰过的完全不重叠。「碰过」指 Read/Grep/Glob 的路径，以及 Bash 里 cat/head/`sed -n` 的文件参数
  - 不用工具、只靠上下文回答的短问题，算「追问」，只进宽松档
- **可省上限**
  - 免费模型：整个回合的花费全部省掉。这是上限，没算换地方问的额外成本，也没算答不好要重问
  - Haiku 新会话（**估计**）：新会话的上下文 = 2.5 万系统提示 + 回合内新增的部分。第一次请求全部写缓存（×2），之后每次读上一次的上下文（×0.1）、写新增部分（×2），输出 ×5。最后整体乘 1/5，这是按 Haiku 单价约为 Opus 的 1/5 估的
  - 扣重建：如果回合第一次请求的缓存写远大于上一回合结束后新增的部分，说明缓存过期、整段重建了。这笔重建费不管在哪里问都要付，只是挪到长会话的下一回合。所以把这部分按缓存读（×0.1）重算，另报一列

## 结果

分母 = 全部等效 token，约 23.4 亿。

| 档 | 回合数 | 占总用量 | Haiku 新会话可省（估） | 免费模型可省 | Haiku 扣重建 | **免费扣重建** |
|---|---|---|---|---|---|---|
| 宽松：所有短的只读回合 | 668 | 6.35% | 5.94% | 6.35% | 2.90% | **3.31%** |
| 严格：只算岔题 | 94 | 0.93% | 0.85% | 0.93% | 0.58% | **0.65%** |

宽松档拆开：

| 类型 | 回合 | 占总用量 | 扣重建后 |
|---|---|---|---|
| 只用 WebSearch/WebFetch（岔题） | 32 | 0.43% | 0.24% |
| 碰的文件和之前不重叠（岔题） | 62 | 0.49% | 0.40% |
| 没用工具，靠上下文回答（追问） | 329 | 1.84% | 0.87% |
| 碰的文件之前碰过，或用了别的工具（追问） | 245 | 3.59% | 1.79% |

- 小问题回合的花费中位数是 9.5 万，平均 22.3 万；开始时的上下文中位数是 47 万。一次请求就要缓存读约 4.7 万，所以单个回合确实贵，只是这类回合加起来不多
- 对照：只看「消息 ≤ 120 字 + 上下文 ≥ 5 万」、不管请求数和改不改文件，有 2046 回合，占 92%。用户的大部分指令本来就很短（「继续」「好的做吧」），所以「短」本身说明不了什么，关键在「不干活、只回答」
- Haiku 估计和免费模型差得不多（5.94% 对 6.35%）：新会话只有 2.5 万上下文，比原来的 47 万小一个数量级
- 分项目：宽松档最高是 Trading-AI 9.3%、ContentScout 9.1%、StockSelector 8.8%；严格档最高只有 1.9%（Trading-AI）

### 阈值敏感性

| 改动 | 宽松（扣重建前 → 后） | 严格（扣重建前 → 后） |
|---|---|---|
| 默认（120 字 / 5 次 / 5 万） | 6.35% → 3.31% | 0.93% → 0.65% |
| 消息 ≤ 60 字 | 5.69% → 3.02% | 0.87% → 0.60% |
| 消息 ≤ 200 字、请求 ≤ 8 次 | 7.63% → 4.19% | 1.33% → 0.89% |
| 上下文 ≥ 10 万 | 6.23% → 3.20% | 0.87% → 0.60% |
| 上下文 ≥ 2 万 | 6.35% → 3.31% | 0.92% → 0.65% |
| 只看最近 7 天 | 6.45% → 3.59% | 0.71% → 0.49% |

最宽的设置扣重建后也只有 4.2%，而且这里面大部分是追问。（日志一直有会话在写，所以几次运行之间回合数差一两个。）

## 抽查（核对判定）

完整的 30 条抽样在原始输出里：全部小问题 15 条，严格档 15 条。

- 宽松档 15 条里，能离开上下文单独回答的只有 3～4 条：「30 AWG 红色硅胶线……是干什么的」「20x 是不是比 5x 多四倍……被官方骗了吗」「我随时按 esc 都会关闭吗」。其余都离不开上下文：追问（「为什么只评价标普？」「这些的有用的概率是？」「花 token 了吗？」「啥情况」）、要操作的指令（「好的开一下游戏我来看」），或者道晚安
- 严格档 15 条里，真岔题约 5 条：澳洲报税、Windows 快捷键、20x 用量、公开的夏普 2 策略、LLM 模拟盘的想法。另外约 10 条是误判：其实是在指挥当前任务（「R9 结束」「现在什么情况」「gogogo 第一天」「M0-M3 直接都做了」），只是碰的文件是新的。所以严格档本身也偏宽，真实的岔题比例更接近 0.3%～0.5%
- 有一条「简单总结目前 ml 都是什么效果」花了 57 万，其中 53 万是缓存重建。这正是「扣重建」要扣掉的情况：换地方问，长会话下一回合照样要重建

## 建议

- **不做 `iu ask`**：能挪走的岔题扣重建后只占 0.65%（而且严格档还偏宽），做一个免费模型问答入口，再加规则让 agent 去用它，收益够不上维护成本，也有答错的风险
- **规则里加一句提醒**（给用户的习惯，不是给 agent 的）：和当前任务无关的问题（报税、产品用量、快捷键之类），最好在新会话里问，不要在几十万上下文的长会话里问。尤其是长会话已经闲了一小时以上、缓存可能过期的时候，问一句就是一次全量重建
- 追问占小问题的大头，但它离不开上下文，挪不走，也不该挪

## 没做的

- 只看了 Windows 日志；Mac 上主要是无人值守的长任务，用户插问的小问题只会更少
- 没有用模型判断「岔题 / 追问」，只用了文件重叠和工具类型这两个启发式；抽查显示严格档偏宽，所以结论只会更保守
- Haiku 的花费是估计：系统提示按 2.5 万，单价按 Opus 的 1/5，没有实测
