# 按难度分流（免费 / Haiku·Sonnet / Opus）+ 递归：可行性（2026-10-19）

数据：Windows 真实日志，过去 7 天，1288 句用户指令，965.8M 等效 token（脚本：`$TEMP/iu/turns.py`，只读本地日志）。
官方文档事实：code.claude.com/docs 的 errors / costs / model-config / prompt-caching / sub-agents / hooks 页。

## 真实花费分布（按「一句话之后实际发生了什么」分类）

| 类别 | 句数 | 花费占比 | 每句平均 | 开始时上下文 | 其中重读旧上下文 |
|---|---|---|---|---|---|
| 轻：≤3 次请求、不改文件 | 517 | 7.3% | 136K | 435K | 54% |
| 中：4~15 次请求、不改文件 | 258 | 12.1% | 453K | 460K | 67% |
| 中：≤15 次请求、改了文件 | 283 | 16.1% | 550K | 431K | 62% |
| 重：>15 次请求 | 230 | 64.5% | 2710K | 434K | 74% |

- 有 288 句是 `<task-notification>`，也就是后台任务回报，不是用户打的字，占 10.2%
- 按模型拆分：Opus 主会话 82.2%，Sonnet 子 agent 11.5%，Fable 4.4%
- 重任务平均 46 次请求、改 7.8 个文件，用过子 agent 的只有 26/230

## 结论

1. **轻任务交给免费模型：上限小**
   - 轻任务占指令数的 40%，但只占花费的 7.3%
   - 抽样看，它们几乎都要靠前文才能答，比如「目前结论是？」「再开一下」「什么模型？」「中文」。没有上下文的免费模型做不了；把上下文给它，又等于把私有会话发出去，而且免费模型的窗口也装不下
   - UserPromptSubmit hook 只能拦下用户的指令，不能不经主模型就直接回答（hooks.md）。所以只能在 Claude Code 外面另做一个入口
   - 现实能省约 1~3%。而且这类任务贵，主要是因为开始时上下文有 435K，300K 压缩已经在压这一块了
2. **中等任务换 Haiku / Sonnet：不划算**
   - 每个模型的缓存是分开的（prompt-caching.md）。会话中途切模型，整段上下文要重新写一遍，切回来还要再写一遍
   - 自己的 A/B：Sonnet 做主线程比 Opus 贵，因为 Opus 用的 token 只有 Sonnet 的 1/4。Haiku 也已经排除
   - 额度：Opus 和 Sonnet 各有自己的模型族限额，此外还有一个所有模型共享的额度。各模型怎么折算没有公开（errors.md）。换 Sonnet 只在撞到 Opus 族限额时有用
3. **递归（把自成一体的子任务交给子 agent）：唯一有大空间的，但省钱靠的是「上下文从零开始」，不是「模型便宜」**
   - 重任务 74% 的花费是在重读开始时已有的 435K 上下文。如果放进约 40K 起步的子 agent，最多能省总花费的 43%
   - 但它和已经装上的 300K 压缩针对的是同一块，**不能简单相加**
   - 还有额外开销：
     - 子 agent 需要一份任务说明，结果还要传回主会话
     - 子 agent 的缓存只保留 5 分钟
     - 主会话要检查子 agent 的结果
   - 以前在小上下文上测过类似做法：交接文件 -11%，耗时 +156%；探索闸门在 Opus 上 -2%。上下文本来就小的时候，好处不明显
   - 只靠提示词让主模型委派，以前被忽略过（探索 0 次调用），需要有机制保证真的委派

## 下一步

1. 零成本：在真实日志上模拟「300K 压缩 + 把重任务放进子 agent」，看比只开压缩多省多少
2. 多省超过 10%，再做小规模 A/B：用 2~3 个接近真实的长 Opus 任务，比较「只开压缩」和「压缩 + 委派 skill」，看质量，并用 `/usage` 核对额度
