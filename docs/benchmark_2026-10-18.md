# 基准测试结果（2026-10-18）

代码：`bench/`。原始数据：`bench/results/`。相关调研：[research/raw/08_hooks_and_limits.md](../research/raw/08_hooks_and_limits.md)、[research/raw/09_prior_benchmarks.md](../research/raw/09_prior_benchmarks.md)。

## 结论先说

1. **免费模型 `auto` 压缩命令输出的质量够用。** 10 类真实输出各跑 3 次：平均命中 97%，最差一次也有 90%，编造位置 0 次，失败 0/30；体积只有 Claude 现在实际看到的 **5.8%**；延迟中位 5 秒，P95 17 秒
2. **单独指定某个免费模型不可靠**：限流导致大量失败（nemotron 26/30 次失败），qwen3.5-397b 还编造了 5 个行号。只能用自动换家的 `auto`
3. **但能省多少有上限**：工具输出只占 Claude 上下文的约 40%（其中「读文件」和「搜索」最多，测试和构建日志不到 1%）。按日志估算，外包长输出**最多**省 Claude 用量的 12%、Codex 的 32%。这是理论上限，实际会更少
4. **别人的实测经验**：这类省 token 工具的节省大多远低于宣传，有的反而更贵（rtk +7.6%、headroom +44%、context-mode +33~72%）。主要原因是缓存会把节省稀释掉，而且信息不够时 agent 会重读、重跑。所以**必须在真实任务上做 A/B 才能下结论**，上面这些都只是必要条件

## 基准 1：真实日志里，上下文装的是什么（只读本机日志，不外发）

### 1a. Claude 主会话（Windows，7 天，155 个会话，11,459 次请求，平均每次请求带 454K token）

| 内容 | 占比 | 平均每次请求带着 |
|---|---|---|
| 助手的工具调用参数（Write 的文件内容、长命令等） | 18.6% | 84K |
| 工具输出：读文件内容 | 18.1% | 82K |
| 工具输出：搜索 | 7.3% | 33K |
| 助手思考（**低估**：日志里只存思考的摘要） | 4.7% | 21K |
| 附件和提醒 | 4.1% | 19K |
| 工具输出：网页/浏览器 | 3.7% | 17K |
| 助手正文 / 用户消息 / 压缩摘要 | 3.3% | 15K |
| 工具输出：脚本、测试构建、git 和其他 | 3.2% | 15K |
| **没解释清楚的部分** | 36.9% | 167K |

- 每 token 对应多少字符，是用 11,335 对相邻请求的实测增量拟合出来的：ASCII 约 2.5 字符/token，中文约 0.65 字符/token
- 固定前缀（系统提示、工具定义等）实测中位数只有 12K，所以那 37% 主要不是系统提示。最可能是完整的思考内容（日志里只有摘要）和截图。**这部分还没验证**

### 1b. 如果把超过 2000 字符的工具输出换成约 1300 字符的摘要（理论上限）

| | 工具输出总花费（等效 token） | 可省 | 占该工具总用量 |
|---|---|---|---|
| Claude（Windows，7 天） | 138M | 91M | 约 12% |
| Codex（Windows，7 天） | 86M | 73M | 约 32% |
| Claude（Mac，7 天） | 9M | 7M | — |

按类别看（Claude / Codex 可省的部分）：

- 读文件内容：59M / 25M
- 搜索：13M / 28M
- 网页/浏览器：13M / —
- 脚本和远程：3M / 9M
- git：1M / 6M
- 测试和构建：**1M / 1M**

**要打的折扣：**

- 为了改文件而读文件，不能换成摘要（Edit 需要原文）。所以「读文件」这一大块能省的远小于表里的数
- Codex 本身会截断长输出（日志里有 "truncated output"），表里已经是截断后的大小

## 基准 2：免费模型压缩的质量

### 语料

10 条，都在 FreeLLMAPI 源码（公开的 MIT 开源项目）的临时副本里生成：在副本里注入已知错误，再跑真实命令。标准答案来自注入的位置和实际输出：

| 语料 | 内容 | 原始字符 |
|---|---|---|
| vitest_fail | 668 个测试，注入 2 个失败 | 134,100 |
| vitest_pass | 668 个测试全过 | 132,829 |
| tsc_errors | 注入 2 个类型错误，加 --listFiles 产生大量输出 | 37,350 |
| vite_build_ok | 构建成功，带一个体积警告 | 7,548 |
| npm_404 | 安装不存在的包，verbose 日志 | 2,917 |
| node_crash | 60 行日志之后，嵌套调用里崩溃 | 3,357 |
| rg_keyless | 搜索出几百行；目标是找出哪些 provider 声明了免 key | 12,639 |
| git_log | 40 个提交的 --stat；目标是找出哪些提交改了 key-parser.ts | 61,955 |
| ask_index_kilo / ovh | 读 654 行的文件，回答问题并给出行号 | 30,408 |

### 分组

- raw_full：完整原样
- raw_30k：Claude Code 现在实际看到的（Bash 超过 3 万字符会截断；这里假设保留前后各 1.5 万，截断方式未核实）
- det：确定性过滤，不用模型（错误、失败、警告行加上下文，目标关键词所在行，最后 20 行，最多 6000 字符）
- llm:*：经 FreeLLMAPI 交给免费模型，每个 3 次

### 结果

| 组 | 平均命中 | 最差一次 | 全对比例 | 编造位置 | 平均字符 | 相对 Claude 实际看到的 | 延迟中位 / P95 | 失败 |
|---|---|---|---|---|---|---|---|---|
| raw_full | 100% | 100% | 100% | 0 | 45,991 | 182% | — | 0 |
| raw_30k（现状） | 94% | 94% | 88% | 0 | 18,327 | 100% | — | 0 |
| det（不用模型） | 88% | 88% | 80% | 0 | 2,717 | 20.9% | 0 | 0 |
| **llm:auto** | **97%** | **90%** | **93%** | **0** | **528** | **5.8%** | 5s / 17s | **0/30** |
| llm:kilo-auto | 78% | 70% | 60% | 0 | 240 | 2.4% | 25s / 94s | 1/30 |
| llm:qwen3.5-397b | 70% | 52% | 37% | **5** | 326 | 3.9% | 2s / 150s | 4/30 |
| llm:nemotron-3-ultra-550b | 13% | 0% | 13% | 0 | 60 | 3.4% | 91s / 92s | **26/30** |

逐条结果见 `bench/results/quality.md`。要点：

- `auto` 30 次里有 28 次实际路由到 `ovh/Qwen3.8-27B`，遇到限流会自动换家。漏掉的只有：git_log 偶尔少列 1~2 个提交，vite 有一次漏了 "built in"
- 现状（raw_30k）在 git_log 上只有 50%：截断把一半答案切掉了。**原样给也不等于信息完整**
- 确定性过滤在 git_log 上是 0%：它分不清某一行属于哪个提交

### 这次测试的局限

- 只有 10 条语料（文献建议 200~300 条），算试点。结论方向可信，具体百分比不精确
- 只测了「摘要里信息全不全」，**没测**付费 agent 拿着摘要能不能把任务做完
- 当时只配了两家免 key 的提供商（OVH、Kilo）。Kilo 免费线路会拿提示词训练，所以只用了公开代码
- 字符到 token 的换算、Claude Code 的截断方式都是估算
