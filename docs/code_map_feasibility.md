# 代码地图（MAP.md）值不值得做：零成本上限测试（2026-10-24）

结论：**不做。** 按事先定的门槛（可省部分 ≥ 15% 才进入第 2 步），真实日志里新会话「改文件之前的探索」只占 4.4%，其中地图能省掉的上限是 1.5%（严格）～ 3.8%（宽松），远低于 15%。第 2 步（`iu map`）和第 3 步（Mac 付费 A/B）都没做，没花额度。

## 怎么测的

脚本：`bench/session_explore.py`（只读 `~/.claude/projects/*/*.jsonl`，不调用模型）。原始输出：`bench/results/session_explore_2026-10-24.txt`。

- 范围：Windows 本机全部 Claude Code 日志，239 个会话文件，30 个项目，约 22.8 亿等效 token。跳过 `subagents/` 和 `isSidechain`
- 新会话：第一条消息没有 parentUuid、sessionId 等于文件名、不是「This session is being continued」。228 个是新会话（Windows 上续聊基本写回原文件，所以几乎都是新会话）
- 等效 token：输入 1、缓存写 2（1h）/1.25（5m）、缓存读 0.1、输出 5，和 iu 账本一致
- 探索期：从会话开始到第一次改文件。改文件 = Edit/Write/MultiEdit/NotebookEdit，或会写文件的 Bash（`sed -i`、`>` 重定向、`tee`、`cp/mv`、Python 写文件等）。中途压缩了还没改，探索期就到压缩为止
- 探索请求：探索期内，工具全是只读探索的请求：Read/Grep/Glob，或每一段都是只读命令的 Bash/PowerShell（ls、find、cat、head、grep、`sed -n`、`git log/show/diff` 等；引号里的 `\|` 不切）。update_plan、ToolSearch 等记账工具不影响判断；ssh 到别的机器、WebSearch、跑脚本不算（地图帮不上）
- 花费 = 请求本身 +「携带」：它读进来的内容在之后每次请求里被缓存读（写缓存 ×2 + 之后每次 ×0.1，到压缩或会话结束）
- Bash 里 cat/head/tail/`sed -n` 的文件参数也算「读文件」，按 cwd 和命令里的 cd 解析成绝对路径
- 可省上限：
  - 严格：读的文件全是「同项目上一个会话读过的」，并且本会话不会改它；ls/grep/find 等定位类在有上一个会话时也算可省
  - 宽松：所有探索请求，只扣掉「读本会话后来要改的文件」（改之前总得读）

## 结果

| 口径（分母 = 228 个新会话的全部等效 token，约 22.8 亿） | 占比 |
|---|---|
| 探索期（第一次改文件之前的全部请求） | 2.0% |
| 其中探索请求本身 | 1.1% |
| 探索请求 + 携带 | 4.4% |
| **严格可省（上一个会话读过 + 不改 + 定位）** | **1.5%** |
| **宽松可省（全部探索，扣掉要改的文件）** | **3.8%** |

- 新会话平均 163 次请求，探索期只有 7.3 次，其中探索请求 4.0 次。真正贵的是后面几百次请求带着大上下文，开头找代码那几次很便宜
- 探索期读的 1194 个文件里：31.9% 上一个会话读过，54.2% 更早的会话读过，10.0% 本会话后来会改
- 分项目：最高是 Chenchengame（宽松 10.6%）、BrainrotGame（9.9%），没有一个项目到 15%
- 73 个「没改文件」的新会话几乎都是 一个小工具项目的 `claude -p` 任务，合计只有 658 万（0.3%），不影响结论

### 放宽到整个会话也不够

如果不限「第一次改文件之前」，整个会话里所有只读探索请求（含携带）占 37.1%，拆开是：

| 部分 | 占比 | 地图能不能省 |
|---|---|---|
| 定位：ls / grep / find / Glob | 12.2% | 只能省一部分：调试中的 grep 多是在找具体字符串、报错、日志行，静态地图回答不了 |
| 读本会话后来要改的文件 | 8.6% | 不能，改之前必须读 |
| 重读本会话已读过的 | 3.7% | 不能，地图不存内容 |
| 第一次读、不改 | 12.7% | 大半不能：按花费 28% 是截图（.png/.jpg），还有 .txt/.output/.log/.json 结果文件；代码和文档（.md/.py/.ts/.cs）约一半 |

就算地图 100% 替掉全部定位和全部「第一次读、不改」的代码/文档，上限也只有约 12.2% + 6.5% ≈ 19%，这是不可能达到的理想值：还没算 MAP.md 本身每个会话的花费（5K token 的地图 ×（2 + 0.1 × 163 次）≈ 9 万等效 token / 会话，约占平均会话 1000 万的 1%），也没算地图过时带来的误导。之前测过的「探索闸门」（把搜代码交给免费 agent）就是同一类做法：Sonnet −11% 但区间跨过 0，Opus −2%，没收录。

### 现成框架（按符号读代码、跨会话记忆）也够不着

另一类工具（serena、token-savior、codebase-memory-mcp、codegraph）不减少探索次数，而是让每次读得更小（按函数/类读，不读整文件）。它们的上限 = 读进来的内容本身 + 之后被反复缓存读的携带。在全部 23.5 亿等效 token 上算（scratchpad 一次性脚本，口径同上）：

| 读的东西（含携带） | 单次 <2K | 2～8K | >8K | 合计 |
|---|---|---|---|---|
| 代码文件 | 1.5% | 2.9% | 1.0% | 5.5% |
| 文档、截图、日志等 | 0.6% | 1.6% | 1.6% | 3.8% |
| 定位（ls/grep/find 的输出） | 1.3% | 0.6% | 0.1% | 2.0% |

按符号读能省的主要是 2K 以上的代码读取，约 3.9%；就算砍掉一半也只有约 2%。这类 MCP 自己的工具清单常驻每次请求（token-savior full 版约 1.1 万 token，core 版也有几千），按平均 163 次请求算约占会话 1%，净收益接近 0。

外面的数字：computingforgeeks 测 token-savior −43%、claude-token-efficient −40%，但只跑 1 次、Sonnet 4.5、任务是「读完 ky 仓库提 3 个改进、不改文件」（几乎 100% 是读代码，正好是我们日志里只占 5.5% 的那部分），也没查结果质量。serena、claude-mem 都没找到独立测试；有人测出 claude-mem 每个会话常驻约 4.2 万 token（旧版）。跨会话记忆（claude-mem、mem0 类）省的是「新会话重新摸项目」，就是上面的严格/宽松可省 1.5%～3.8%。

### 「记忆不好会降智」查了吗

查了，分三种（只读日志，scratchpad 一次性脚本；用户消息去重，长度 ≤ 400 字，纠正正则同 `bench/compact_quality.py`）：

| 情况 | 日志信号 | 现状 |
|---|---|---|
| 压缩后忘了用户的要求、决定 | 压缩后前 3 句纠正率 3/173 = 1.7%，其余时候 13/1709 = 0.8%；人工看 3 条里只有 1 条像失忆 | 受控实验里最严重：不记笔记 0/16。NOTES.md + hook-compact 后 16/16，Windows 已装新版 |
| 上下文太长变迟钝 | — | 提前压缩（约 30 万）正好对冲；外部记忆框架往上下文里加东西会加重 |
| 跨会话失忆（新会话不知道上次的决定、坑） | 新会话前 3 句纠正率 2/331 = 0.6%，不比平时高；「上次/又/每次」类 7 条，人工看只有 1 条是真的跨会话失忆 | CLAUDE.md + 自动记忆 MEMORY.md 在管 |

代码地图记的是「文件在哪」，降智主要来自忘了「用户要什么」，两者不是一回事。局限：正则只抓得到用户说出口的不满，模型悄悄做差、用户没发现的抓不到，那要靠受控实验。

### 跨会话失忆的受控实验（2026-10-24，付费一次）

脚本 `bench/pelican_cross.py`（Mac，Claude Code 2.1.283，Sonnet，每组 1 次）。第一个会话分 6 条消息定好加难版鹈鹕的 16 条细节（含 3 次改动），结束；开全新会话（不 `--resume`），只说「按上次定好的规格画，包括后来的改动」。规格、打分沿用失忆鹈鹕（`bench/pelican_check.py` 加难版）。结果在 `bench/results/pelican/cross_runs.jsonl`、`claude_cross_N_1.png`。

| 组 | 第一个会话 | 新会话结果 | 等效 token（会话 1 + 2） |
|---|---|---|---|
| X：什么都不做 | 只回 noted | **0/16**：查了自动记忆（空的，Claude Code 一个记忆文件都没写）和目录，找不到，请用户重发规格，没有乱编 | 5.2 万 + 5.4 万 |
| N：按 skill 第 3 节记 NOTES.md | 每段都写进 NOTES.md，16 条全记对 | 没有任何提示，第一步就 `cat NOTES.md`，画出来脚本判 15/16，人工复核 **16/16**（扣的「7 只鸟」是描边写在外层 `<g>` 上，打分脚本的老问题） | 12.6 万 + 19.8 万 |

- 合计约 43 万等效 token，Sonnet 约 1.3 美元
- 原计划的 H 组（新会话开始时用 hook 把 NOTES.md 塞进上下文）没跑：N 组不用 hook 就已经满分
- 结论：跨会话不靠新框架，靠「每条要求都记进 NOTES.md」这个现有做法就够；不记的话新会话会老实说不知道，表现为用户要重说一遍，而不是悄悄做错
- 局限：每组只有 1 次；新会话的提问里提到了「上次定好的」，它才会去找

### 新会话完全不提上次（加测，付费一次）

同上，但新会话只说「画一只骑自行车的鹈鹕，写到 pelican.svg」（`--final plain`）。两组第一个会话都记 NOTES.md（分别 18、19 行，规格都记全了）。

| 组 | 新会话 | 结果 | 等效 token（会话 1 + 2） |
|---|---|---|---|
| N：只有 NOTES.md | 直接画，没读 NOTES.md | **1/16**（只有「没有头盔」碰巧对），蓝天沙地、黑色车架、画布只画了左上 400×300 | 13.3 万 + 3.9 万 |
| H：NOTES.md + 开场 hook（SessionStart `startup`，把 NOTES.md 原样塞进上下文） | 直接按规格画，再自己 grep 检查禁用颜色 | **16/16**（打分脚本也是 16/16） | 12.1 万 + 11.5 万 |

- 两次加测合计约 41 万等效 token，Sonnet 约 1.2 美元；跨会话测试一共约 2.5 美元（后来补了重复实验，见下）
- 结论：NOTES.md 只在用户提到「上次」时才会被读；不提就等于没记。开场 hook 能补上这个缺口：1/16 → 16/16
- 代价：每个新会话多带 NOTES.md 的内容（这次约 1 KB）；只影响项目根目录有 NOTES.md 的项目
### 重复实验：每组 3 次（2026-10-25，用来做视频，付费）

设置和第一次完全一样（`bench/pelican_cross.py`，Mac，Sonnet；第一次的 X 组是「提上次」，H 组是「不提上次」，所以分别按原设置补；「不提上次」的 X 组另补 3 次，好和 H 组直接对比）。每次的 SVG/PNG 在 `bench/results/pelican/claude_cross_*`，记录在 `cross_runs.jsonl`。分数：打分脚本 / 人工复核。

| 新会话怎么问 | 组 | rep 1 | rep 2 | rep 3 |
|---|---|---|---|---|
| 提「上次定好的规格」 | X：不记笔记 | 0/16 | 0/16 | 14/16 / 人工 16/16，**串到其他测试的记录**（见下）；隔离重跑 3b：0/16 |
| 提「上次定好的规格」 | N：记 NOTES.md | 15/16 / 人工 16/16 | — | — |
| 完全不提上次 | X：不记笔记 | 1/16 | 1/16 | 1/16 |
| 完全不提上次 | N：只有 NOTES.md | 1/16 | — | — |
| 完全不提上次 | H：NOTES.md + 开场 hook | 16/16 | 15/16 / 人工 16/16 | 16/16 |

- 「不提上次」时 X 组的 1/16 都只是「没有头盔」碰巧对；没有一次乱编规格。「提上次」时 X 组不记笔记的正常结果是请用户重发
- H rep 2 脚本扣的「太阳 8 道光芒」：太阳正好 8 道 `#FB8500` 光芒，脚本把同色的鹈鹕腿（一条 `#FB8500` 的线）也数成光芒；人工 16/16
- X rep 3 脚本扣的「7 只鸟」「12 根辐条」：图里正好 7 只鸟、12 根辐条（描边写在外层 `<g>` 上，加上同色的脚踏曲柄，脚本的老问题）；人工 16/16。但这一次不算数：新会话被问到「上次」，自己去 `~/.claude/projects/` 列了所有 pelican 目录，读了**另一次测试（X rep 2）**第一个会话的完整记录，那次的规格一模一样，于是照抄回来。照实保留，标成「串到其他测试的记录」
- X rep 3b（隔离重跑）：跑之前把以前鹈鹕测试的 18 个会话记录目录（`~/.claude/projects/-private-tmp-pelican-*`）和 25 个工作目录（`/tmp/pelican/*`）临时挪走，只留这次自己的；跑完全部挪回（核对过数量）。结果 0/16：它查了自己项目目录（里面就有第一个会话的记录文件），没去读，最后请用户重发
- **发现：被问到「上次」时，Claude Code 会主动去翻磁盘上的旧会话记录（`~/.claude/projects/` 下的 .jsonl），同一项目的旧记录也算一种记忆来源。** 但它不可靠：4 次「提上次、不记笔记」里只有 1 次翻到并用上了，而且那次翻的是别的项目。靠得住的还是 NOTES.md + 开场 hook
- 花费（Sonnet，等效 token × 3 美元/百万）：这批 8 次（X 提上次 rep 2、3、3b，H rep 2、3，X 不提上次 rep 1~3）合计约 3.45 美元；跨会话测试累计 12 次约 5.95 美元

- 已做进 iu（2026-10-24）：`iu/hook.py` 的 `compact_context` 接受 `startup`（开场版不带「笔记之后的用户原话」，提示写明「只遵循相关的，和用户最新的话冲突时以用户为准」，超过 9000 字截断并提示去读全文）；`iu install` 在 SessionStart 下装 compact、startup 两条（`--no-notes` 都不装）；`resume`、`clear` 不塞。测试 `tests/test_hook_compact.py`、`tests/test_install.py`，全部 58 个通过
- 实验里用的是 `bench/pelican_cross.py --hook-startup`（同样的做法，文字略有不同），产品版 hook 还没在真会话里跑过。2026-10-25 已在 Windows 重新 `iu install`（settings.json 的 SessionStart 有 compact、startup 两条，拿装好的命令喂 startup 输入能输出 NOTES.md）；Mac 还没装

## 抽查（核对口径）

用 `--show N --seed S` 打印探索期明细，抽了 10 个左右会话人工看：

- BrainrotGame/495a7286：探索期 42 次请求，几乎全是 `cat`/`sed -n`/`grep` 读 Unity 脚本，第 42 次 `mkdir && cat >` 写文件。判对了；这是全体里探索最重的会话之一，探索 + 携带也只占它 1750 万里的约 10%
- InfiniteUsage/29e01ae7：先 `ls`、`cat iu/hook.py iu/install.py`、`grep` 文档，第 10 次 `cat >> iu/hook.py` 写文件。修正前 `grep "a\|b"` 被当成管道切开误判为「其他」，已修
- FloatingDesign/48525840、Trading-AI 两个会话：探索期主要是 WebSearch / ssh 到 Mac，正确地没算成可省
- 一个小工具项目的 `claude -p` 任务：读 2～3 个文件就回答，没有改文件，整段算探索期
- 已知偏差：写到临时目录（scratchpad）也算「第一次改文件」，会让探索期略短；`for` 循环、`python -c` 读文件不算探索，会略低估。两者都是百分之零点几的量级，不改变结论

## 没做的

- 第 2 步 `iu map`、第 3 步 Mac A/B：门槛没过，按计划停下，没花额度
- 只看了 Windows 日志；Mac 上的日志没跑（Mac 主要是无人值守长任务，探索占比只会更低）

## 换成 Codex 和 OpenCode：跨会话失忆鹈鹕（2026-10-25）

同一套跨会话测试（`bench/pelican_cross.py --host codex|opencode`，新会话完全不提「上次」，也就是 `--final plain`），在 Mac 上每组跑 1 次：

| 组 | OpenCode（免费 deepseek-v4.1-flash-free） | Codex（gpt-6-sol，推理强度 medium） |
|---|---|---|
| X 不记笔记 | 1/16 | 2/16 |
| N 记 NOTES.md，没有新规则 | 16/16（见下面说明） | 2/16 |
| R 记 NOTES.md + 规则「新会话开始先读 NOTES.md」（写进项目 AGENTS.md） | 16/16：第一步就是 `test -f NOTES.md && cat NOTES.md` | 16/16：第一步列出 NOTES.md，然后 `cat NOTES.md` |
| H 记 NOTES.md + 自动塞回（OpenCode 插件 / Codex SessionStart hook） | 16/16 | 16/16：会话记录里有 hook 塞进去的笔记，说明 hook 触发了 |

- Codex 和 Claude 一样：只记笔记、新会话不提上次时，笔记写了也不去读（Codex 2/16，Claude 1/16）。所以光有笔记不够，得有规则或者 hook
- OpenCode 的 N 组得 16/16，是因为 Mac 上 OpenCode 全局 AGENTS.md 里的旧规则让它先加载 skill、跑 `iu agents`、看目录，顺路读到了 NOTES.md。这算旧规则加 skill 的功劳，不能当成「OpenCode 天生会读」
- 所有组的全局说明文件都一样（Mac 上装的是旧版 iu 规则：先加载 infiniteusage skill），每组之间只差项目里的那一样东西
- 花费：OpenCode 免费；Codex 4 组合计约 72 万等效 token（不算缓存读的话更少），Codex 周额度从头到尾都是 43%，也就是不到 1%
- 每组只跑 1 次，样本小；Claude 那边是每组 3 次（见上一节）

产品改动：

1. 常驻规则（Claude Code、Codex、OpenCode、Qwen Code 的全局说明文件）加一条「每个新会话开始时，如果项目根目录有 NOTES.md，先读它再动手」，就是 R 组测的那条
2. `iu install` 在 Codex 上往 `~/.codex/hooks.json` 加 SessionStart（startup、compact）→ `iu hook-compact`。Codex 传给 hook 的 payload 和 Claude Code 一样，所以用的是同一个命令。Codex 要求先信任 hook（实测：没信任时不运行），用户要在 Codex 里输入 `/hooks` 信任一次。Windows 上先不装，因为 Codex 在 Windows 上用什么 shell 执行 hook 没验证过
3. （2026-10-25 起不再装：宿主只做 Claude Code 和 Codex，OpenCode 只当免费工人；插件留在 `bench/opencode_notes.js` 复现用）当时 `iu install` 在 OpenCode 上放一个插件 `~/.config/opencode/plugins/infiniteusage-notes.js`，通过 `experimental.chat.system.transform` 把 NOTES.md 放进系统提示。每个会话只读一次，压缩后再重读，所以笔记改了也不会让缓存作废
